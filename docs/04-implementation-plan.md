# cesiumlab V1.0 分阶段实施计划

> 文档编号：CL-PLAN-001

> 上游：[`01-product-requirements.md`](./01-product-requirements.md)、[`02-technical-architecture.md`](./02-technical-architecture.md)、[`03-agent-specification.md`](./03-agent-specification.md)

## 1. 目标、策略与交付定义

以最小的真实 CesiumJS 实验推动架构成熟，不先建复杂平台。按依赖顺序完成：

```text
S0 仓库基础 → S1 最小 Web / Cesium 环境 → S2 首个视觉实验
           → S3 视觉检查与人工验收 → S4 公开 Playground 稳定展示
                                          │
                                          ▼（存在合格候选且用户批准时）
                                     S5 npm 通用化候选与独立验证
                                          │
                                          ▼（再次批准时）
                                     S6 正式 npm 发布（可晚于 V1.0）
```

**Milestone A：Visual Lab** = S0–S4；**Milestone B：Reusable Library** = S5（不强制首个实验晋升）。S6 为可选正式发布阶段，不应为了凑版本号而提前执行。

实施默认采用 pnpm / Vue 3 / Vite / TypeScript / CesiumJS / Vitest / Playwright，详见架构文档。依赖版本必须在实施时核实并用锁文件固定，不能从本计划推测固定版本已验证。

## 2. 全局执行纪律

- 用户提供视觉目标和验收反馈；Coding Agent 负责全部编码与检查，不要求用户改动源码。
- 当前**尚未提供具体首个视觉参考**。S0–S1 可先执行，但 S2 不得将“雷达扫描”之类示例擅自当作已经选定的复现目标。可采用中性渲染 smoke test 验证框架，但它不算首个 Visual Approved 实验。
- 每阶段先完成最小验收，再追加功能。遇到缺失浏览器/GPU/素材权限时，提供准确的阻塞说明与可执行的替代验证，不伪造通过状态。
- 不在开发正常实验的同时建设不必要的 UI 框架、插件市场、完整状态机、远程执行系统。
- Git 保留可回退变更。若当前已有仓库内容，先读现有代码、锁文件和配置；不得盲目覆盖。

## 3. S0：仓库与执行规范

### 目标

建立安全、最小、可重复安装的 Monorepo 骨架，不启动正式的 npm 发布流程。

### 任务

1. 初始化仓库或检查既有仓库，配置 `.gitignore`、README、基础许可证状态说明、Node/pnpm 版本约束和锁文件。
2. 创建 `pnpm-workspace.yaml`，覆盖 `apps/*`、`packages/*`；`experiments/` 可先作为普通源码目录，**无需每个实验都独立成为 workspace package**。
3. 引入本文档体系与根目录 `AGENTS.md`。
4. 配置基础的格式化、Lint、类型检查及测试入口；避免一次引入多个重复的任务编排工具。
5. 确定默认本地启动路径、错误报告位置、依赖版本固定策略；明确公开源代码许可证尚待正式决定时的限制。

### 产物

仓库最小骨架、依赖锁定、可供 Agent 导航的 README / AGENTS.md、基础检查命令。

### 退出条件（Gate S0）

- 全新工作副本可按 README 安装依赖并通过基础静态检查。
- 无应用秘密或第三方未授权参考素材进入 Git。
- 未来添加 `packages/*` 不要求重做根工程布局。
- S0 不必创建没有真实实现的 `@cesiumlab/effects` API 或伪造 npm 版本。

## 4. S1：最小 Web + CesiumJS 实验环境

### 目标

证明纯 Web 架构能够正确加载 CesiumJS、静态资源与一个中性三维场景。

### 任务

1. 创建 `apps/playground`，使用 TypeScript + Vite + 简洁 Vue 界面，不建设大型设计系统。
2. 配置 CesiumJS `Workers`、`ThirdParty`、`Assets`、`Widgets` 静态资源与 `CESIUM_BASE_URL`；注意赋值与依赖加载顺序。
3. 用不要求私密 Cesium ion token 的基础场景完成烟雾测试，例如一个可控制相机的地球/几何体；严格标注为 **Smoke Test** 而非视觉复现成果。
4. 实现基础的加载中、加载失败、WebGL 不可用提示；浏览器关闭/页面卸载时释放 Viewer。
5. 建立最简单 Gallery / Detail，可通过纯元数据展示至少一个示例条目；目前允许手工登记，不引入自动发现框架。
6. 保证构建后的静态站点可预览，特别检查非根路径部署时 Cesium Workers 是否可访问。

### 产物

可启动的 Playground、基础 Viewer、最简实验档案页及静态资源配置。

### 退出条件（Gate S1）

- `dev` 与 `build/preview` 都能实际渲染场景；Cesium Workers/Assets 网络请求正确。
- Chrome/Chromium 桌面环境可旋转、缩放基础场景；有截图或明确注明工具无法进行视觉测试。
- 一个错误的实验详情不应破坏站点导航；没有注册的实验代码不会自动进入构建。
- 不要求 Gallery 搜索、沉浸双模式、多模型管理等扩展功能。

## 5. S2：首个视觉参考实验

### 前置输入与确认

需要一份**具体的视觉目标**，可为用户后续提供的图片/视频/GIF 或描述。项目计划先于素材完成，因此此输入是未来任务的外部依赖，不在文档中伪造。可使用用户有权提供/公开的参考；若来源不能公开，实验说明保留非敏感描述与授权展示截图。

### 目标

证明 Coding Agent 能从视觉参考独立完成一项真实 CesiumJS 视觉实验，并提供可观察的结果。

### 任务

1. 建立 `experiments/<slug>/`，包含最小元信息、运行入口、简明 README、展示参数与可公开的资源。
2. 对参考做视觉拆解，列出可观察特征和推断出的动画/空间假设。
3. 选择首选技术路线；除非出现实质性问题，不强制先实现多个对照版本。
4. 实现精心设置的默认相机与视觉参数，确保打开实验后无需复杂准备即可看到目标效果。
5. 提供少量真正影响效果的控件（若适用），无需为通用性抽取大型 Runtime。
6. 真实启动应用，检查 Shader 编译、网络请求、控制台、渲染和基本交互；动态特效在不同时间点检查。
7. 自主修复明显问题并留下技术摘要与未解决差异。

### 产物

一个 `experiments/<slug>`、真实展示入口、技术说明、实际渲染证据、关键参数和 Git revision。

### 退出条件（Gate S2）

- 实验可在浏览器运行并产生**实际 CesiumJS 渲染输出**，或提供透明的技术不可行/未验证记录。
- 视觉参考来源和公开权限已处理；无敏感资源泄漏。
- 能在 Playground 看到/返回该实验或看到其明确错误状态。
- 不宣称已经通过视觉验收。

## 6. S3：视觉验收与可重复观测

### 目标

将“看着差不多”转为可追溯的实际视觉决策，不把人工审美外包给 Agent。

### 任务

1. 记录与参考可比的分辨率/画面比例、相机位置、关键参数及动画采样状态。
2. 提供实际渲染截图；动态效果补充关键帧或真实录制（若工具可用）。
3. 分项对比形态、色彩、光影、动画、遮挡/空间关系、细节；明确未满足项。
4. 发现问题则修改并重新验证；对无法克服的技术差异说明理由和替代路径。
5. 用户明确接受后标记 `Visual Approved`，固定对应的源码 revision 和视觉基准。

### 产物

视觉验收记录、获准的基准画面/配置，以及改进后的可运行实验。

### 退出条件（Gate S3）

- **必须得到用户实际的视觉批准才能称 Visual Approved**。
- 如果用户不批准，S3 保持开放，允许继续迭代；不能为了后续 S5 强行跳过。
- 如果视觉检查工具缺失，记录未完成项目，不把构建成功描述为视觉通过。

## 7. S4：公开 Playground 的最小稳定发布

### 目标

兑现“所有实验公开可见”的产品决定，同时保证一个损坏的实验不会轻易拖垮整个网站。

### 任务

1. 将所有**已登记**实验的安全元数据纳入公开 Gallery，包含 Idea、Prototype、Approved 等成熟度；运行状态单独标注。
2. 运行中实验按需加载，未完成的只显示详情；失败入口有说明或安全回退。
3. 对公开素材做许可和敏感信息检查。将原始研究参考与可公开部署素材分开；无授权时不显示原文件。
4. 添加部署前构建、静态资源检查和可运行实验基本浏览器冒烟检查。部署失败不得覆盖上一版本。
5. 选择适合静态 Web 的托管平台（例如 GitHub Pages / Cloudflare Pages / Vercel 中一种），验证 base path、资源 URL、CSP 与缓存；部署平台是技术选择，不改变产品架构。
6. 对所有已登记实验保持链接稳定；发布失败的实验可以显示 `Unavailable`，但不能凭手写状态声明“可运行”。

### 特别说明：构建故障隔离

简单 `import.meta.glob` 引入坏掉的 TypeScript/GLSL 模块不能保证全站仍成功构建。V1.0 可采用**人工筛选已验证入口**：纯元数据一律展示，只有通过构建检查的实验才进入生产代码导入表。实验增多以后，再升级为“独立入口构建/校验 + 生成目录”，不得为了实现这一特性提前建造复杂远程运行平台。

### 产物

公开静态 Playground URL（当部署授权和平台可用时）、公开实验列表、部署检查结果与回退方案。

### 退出条件（Gate S4）

- 网站上所有已登记实验均有可访问的档案，不强制全部能运行。
- 首个真实实验可从 Gallery 到达；可运行状态与实际检查一致。
- 无私密 token、无不具备许可的原始第三方素材或未经审核的任意执行入口。
- 构建/部署失败时公开站点不因本次失败被覆盖。

**Milestone A 通过标准**：S0–S4 核心检查完成，且至少一个真实参考驱动实验已经通过用户视觉验收。如果没有参考或用户尚未确认，报告“环境就绪/等待视觉批准”，不得伪报 A 完成。

## 8. S5：npm 特效候选与独立工程验证

### 启动条件

存在视觉已批准且明确具有复用价值的候选；用户已同意进入通用化。若首个实验不适合，继续保留为实验，选择后续候选。

### 任务

1. 写出该特效的适用场景、不支持条件、依赖和预期 API；参数应围绕视觉行为。
2. 在 `packages/effects` 中实现独立 ESM + TypeScript 声明包，Cesium 版本范围按测试结果确定，优先考虑 peer dependency 策略。
3. 将成熟实验的演示改为消费本地构建包，而不是继续平行维护两套重复实现；必要时保留原 prototype 作为历史快照。
4. 验证重复创建/销毁、失败路径释放、参数更新和场景设置恢复。
5. 通过 Vitest/类型/包导出检查及必要 Playwright 视觉回归；实际运行至少在声明的基础环境中通过。
6. 执行 `npm pack`（或与所选包管理器兼容的 tarball 流程），在**独立消费项目**安装该 tarball 并验证导入、构建、运行和清理。
7. 检查 npm 包文件清单中没有参考视频、私钥、内部调试内容；补齐 README、LICENSE、API 与限制说明。

### 产物

一个**发布候选** npm 包、独立消费演示或测试项目、质量/兼容性报告、视觉回归记录。

### 退出条件（Gate S5）

- 依赖方向正确，消费端不需要仓库内部源码、路径别名或 Playground。
- 通过声明范围内的真实运行和资源管理测试。
- 对照 Visual Approved 基准无不可接受退化；退化时回到视觉批准关口。
- npm scope 所有权、许可证仍未解决时，**不能进入发布**，但可完成本地打包验证。

## 9. S6：正式 npm 发布（独立审批阶段）

S6 **不自动属于 V1.0 的完成要求**。执行条件为项目所有者明确批准一个确定的版本及包：

1. 确认 `@cesiumlab` scope/包名可用且有发布权限；确认代码许可证、第三方授权及资源分发权。
2. 确认版本语义和兼容范围，整理 CHANGELOG、README、升级指南（如有破坏性变化）。
3. 审核 `npm pack` 清单、包依赖、类型声明及 sourcemap 是否泄露不应公开的信息。
4. 配置安全发布凭据；若采用可信发布，按 npm 官方方式配置 OIDC、工作流绑定和 provenance。
5. 执行经批准的发布操作，核验 registry 安装、包页面、版本与源代码关联；失败时记录状态，避免重复推送错误版本。

不承诺发布必然成功，也不要求 Agent 静默执行外部不可撤销操作。

## 10. 回归矩阵与测试证据

| 变更             | 最低必检项目                           | 额外检查                         |
| ---------------- | -------------------------------------- | -------------------------------- |
| 基础 Web 配置    | 构建/预览/Workers/Assets/Viewer 初始化 | 非根路径部署                     |
| 新增实验         | 元数据/入口/真实渲染/回退              | 动画/专用资源加载                |
| 修改视觉效果     | 参考差异、当前基准、重要参数           | 自由相机和特殊角度               |
| 修改公共 Runtime | 已有实验加载、切换、销毁               | 多次来回切换后资源占用           |
| 修改包 API       | 类型、构建、独立安装                   | 升级路径、多个实例               |
| 准备发布         | 许可证/敏感文件/清单/版本/用户批准     | trusted publishing 与 provenance |

所有证据记录最少包括：执行命令、环境、结果、实际截图/录制路径（若有）、Git revision、**未验证项**。截图基线尽可能在相同浏览器/OS/GPU 环境对比。

## 11. AI Coding Agent 任务切分建议

| 任务包 | 推荐 Agent 任务范围              | 禁止跨越                    |
| ------ | -------------------------------- | --------------------------- |
| T01    | 仓库与文档集成、基础检查         | 不创建虚构 npm API          |
| T02    | Web/Cesium 烟雾测试、资源与构建  | 不冒充视觉实验成功          |
| T03    | 选定参考的视觉原型、真实运行证据 | 不擅自标 Visual Approved    |
| T04    | 基于用户反馈的视觉迭代与基准保存 | 不擅自发布包                |
| T05    | 公共 Gallery、状态与部署安全     | 不隐式公开参考原件          |
| T06    | 已批准实验的包候选与独立消费验证 | 不擅自改变公开 API 稳定承诺 |
| T07    | npm 发布候选整理、授权后发布     | 未经批准不得 publish        |

每个任务包完成需按 `docs/03-agent-specification.md` 第 9 节报告。不要把 T03–T07 合并为一条没有检查点的长任务。

## 12. 常见失败与回退

| 情形                       | 立即行动                                        | 可接受结果                 |
| -------------------------- | ----------------------------------------------- | -------------------------- |
| 无可用视觉参考             | 完成 S0–S1；保留 smoke test，不假称参考复现完成 | 等待真实视觉输入           |
| 视觉参考依赖复杂未授权模型 | 使用授权替代场景，同时标出差异和限制            | 可运行原型但未必视觉批准   |
| 代码能编译但 WebGL 失败    | 收集控制台、硬件、资源请求；隔离失败入口        | 公开档案保留，运行状态真实 |
| 自动化浏览器无 GPU         | 记录未验证，提供人工检查入口和步骤              | 不通过自动视觉 Gate        |
| 通用化后视觉退化           | 回退或重新提交用户确认                          | 暂不晋升 npm 候选          |
| 单实验阻断站点构建         | 排除坏入口、保留安全元数据；修复后再纳入        | 其余站点可部署             |
| 外部消费测试失败           | 停止发布、修正包导出/依赖/资产                  | 包保持候选状态             |
| npm 名称或许可证不确定     | 完成本地 tarball 测试，阻止 publish             | 发布门槛未通过             |

## 14. S0–S4 完成后的需求复盘

完成首个真实实验后进行短复盘：

1. 实验增加速度的瓶颈在视觉实现，还是 Playground 接入？
2. 是否至少两个实验需要相同的 Viewer 生命周期/参数组件？没有则暂不抽象。
3. 是否经常因图形设备、模型资源或环境配置导致复现困难？若是，优先改善验证环境。
4. 是否有真正可以封装的共同特效能力？没有则先增加实验，不制造空包。
5. 公共 Gallery 的实验数量和访问行为是否证明分类搜索、自动发现值得做？无证据则继续轻量维护。

只有这次复盘识别出重复问题，才把自动发现、标准参数协议、更多测试场景等 P1 需求提到下一版本。
