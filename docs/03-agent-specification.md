# cesiumlab AI Coding Agent 研发与交付规范 V1.0

> 文档编号：CL-AGENT-001  
> 日期：2026-11-08  
> 规范属性：**原则与质量要求**；仓库根目录 [`AGENTS.md`](../AGENTS.md) 是 Agent 执行时的简明入口。  
> 相关文档：[`01-product-requirements.md`](./01-product-requirements.md)、[`02-technical-architecture.md`](./02-technical-architecture.md)、[`04-implementation-plan.md`](./04-implementation-plan.md)

## 1. 任务使命

Agent 的任务不是生成尽可能多的特效，而是：**将用户提供的视觉参考转化为真实运行、可以反复验证的 CesiumJS 视觉实验；用户确认满意后，将具有明确复用价值的实现提炼为独立、可信的 npm 模块。**

首要优先级：

1. 不伪造事实、运行结果、测试或视觉证据。
2. 不破坏既有、已验收的视觉表现以及已有成果。
3. 视觉实验阶段优先满足视觉目标，选择有效而非炫技的技术路线。
4. 包阶段优先契约、稳定性、正确释放、兼容性和独立消费能力。
5. 保持架构简洁，不在真实需求出现前建造平台型基础设施。

## 2. 任务分类与阶段

### 2.1 Creative / Visual Experiment

输入：图片/GIF/视频/概念描述、用户观察反馈、（可选）指定模型与场景。

Agent 职责：视觉拆解 → 提出必要技术假设 → 从零实现 → 启动并观察真实渲染 → 修正明显缺陷 → 提交用户视觉验收。不得为了提前满足 npm 规范而不必要地降低视觉效果。

输出：实验入口、可运行页面或明确的不可运行原因、实际视觉证据、技术说明、已知限制和 revision。

### 2.2 Engineering / Generalization

输入：已 Visual Approved 的实验以及用户“进行封装”的明确批准。

Agent 职责：复用价值评估 → 提取稳定模块 → 设计简明 API → 生命周期管理 → 类型与测试 → 外部消费项目验证 → 与视觉基准比对。

输出：独立模块候选、API、示例、测试结果、兼容性说明与视觉回归证据。未达标准不提交正式发布。

### 2.3 Maintenance / Release

输入：故障、依赖升级、安全问题、正式发布请求。

Agent 职责：控制变更范围、兼容性评估、回归测试、变更记录、npm 包清单检查；破坏性 API 或架构迁移要先批准；正式 npm 发布需用户批准。

## 3. Agent 自主权与审批矩阵

| 操作                                         | 权限               | 必须做什么                           |
| -------------------------------------------- | ------------------ | ------------------------------------ |
| 研究 Cesium API/技术、比较方案               | 自主               | 记录核心技术判断                     |
| 新建/修改未发布实验、调参、试错、运行测试    | 自主               | 不破坏其他实验；保留变更记录         |
| 安装常规开发依赖、调整实验内部实现           | 自主，按最小权限   | 说明新增依赖及其必要性               |
| 修改共享 Runtime、构建系统                   | 可执行但需影响评估 | 检查所有受影响实验；大范围迁移先提案 |
| 宣告视觉通过                                 | 无权               | 等待用户明确确认                     |
| 将某实验晋升为正式候选                       | 需确认             | 提供复用价值与限制评估，获准后推进   |
| 变更已发布包的破坏性 API                     | 需先批准           | 提交迁移、SemVer 与受影响范围        |
| 删除历史/重写 Git、改变许可证、公开私有素材  | 需先批准           | 不能为了方便而自行操作               |
| 使用外部服务付费额度、创建公开资源、发布 npm | 需先批准           | 明确产生的影响、权限及撤销路径       |

Agent 不应要求用户批准每个变量名、Shader 参数或普通缺陷修复；用户的主责是**视觉方向和关键发布决策**。

## 4. 视觉实验 SOP（可执行工作规程）

### Step V-01：输入理解

- 提取**可观察事实**：颜色、几何、空间层次、发光、运动、相机视角。
- 分离**不可观察推断**：静态图中动画方向、实际光源机制、深度效果。
- 识别需额外资产（模型/纹理/地形）及授权来源；没有时优先采用可公开使用的轻量资源。
- 遵守“忠实复现默认；技术受限时视觉适配；未经要求不创意改造”。
- 若用户尚未提供具体参考，只建设最小能运行的实验空壳或 smoke test；**不能编造已选择的视觉目标**。

### Step V-02：技术判断

- 简短说明首选路线，例如 Entity / Primitive / Material / CustomShader / PostProcessStage / ParticleSystem。
- 只在存在重大不确定性时比较多种方案；优先能满足视觉目标、可实际验证且维护风险合理的实现。
- 私有 API、实验性 API、第三方包、WebGL 限制、深度纹理、透明排序等风险需要提前标出。
- 不照搬参考作品的未知源码；如查阅公共文档学习 Cesium API，遵守相应许可证。

### Step V-03：最小可运行实现

- 实现真实 CesiumJS 渲染，不使用 AI 生成图片伪装成程序输出。
- 优先用专用场景满足视觉参考；不强制单个 Effect 或单一 Viewer。
- 包含足够的默认相机、视觉参数和必要动画让用户直接观察。
- 保持模块与资源所有权可理解；实验退出时至少不会继续无意义地占用资源或污染共享场景。

### Step V-04：真实运行与自检

- 启动应用，验证本地构建/访问、资源加载、控制台和 WebGL/Shader 运行状态。
- 捕获**真实渲染**截图；动态效果检查至少两个有意义的时间点或可见运动证据。
- 优先以与参考相近的画面比例、相机、动画时刻进行视觉比对。
- 检查主要形态、色彩、光影、动画节奏、遮挡/深度关系和明显瑕疵。
- 视觉问题能够修正时自主修正并复验；连续尝试无改善时说明瓶颈，停止无意义循环。

**环境限制处理**：若没有可操作的浏览器/GPU/录屏设施，只报告实际完成的静态构建和逻辑测试，并标识视觉项“未验证”；不得声称“已实际查看”“视觉符合参考”。用户仍可通过可运行网页完成人工验收。

### Step V-05：提交视觉验收

交付必须回答：

1. 在哪里看到真实可运行的结果？若无法提供 URL，则给出可运行入口与正确的本地命令。
2. 最终渲染证据是什么？截图/录屏与源码 revision 是否对应？
3. 与参考相比，哪些核心特征已经实现，哪些仍有差异？
4. 主要用了什么技术、为什么、有什么限制？
5. 你需要用户做什么判断（接受、继续修改、停止或重做）？

用户明确通过后记录 Visual Approved，保存实际对照状态；不允许 Agent 自行代替用户审批。

## 5. 通用化 SOP（只在批准后执行）

### Step E-01：适用性评估

- 目标问题是否具备稳定的重复使用价值？若仅与一个特定视觉作品紧耦合，允许继续只作为 Experiment。
- 写明支持对象：Entity、Model、3D Tiles、场景后处理或特定类型，不承诺无条件兼容。
- 确认对模型坐标、深度、透明排序、Cesium 版本及外部资产的依赖。

### Step E-02：API 最小化设计

- 默认简单易用，参数围绕视觉行为命名：颜色、范围、速度、强度等。
- 不暴露没有实际消费者需要的内部 Shader 常量。
- 对高级用户保留适度扩展，但不给未成熟能力稳定承诺。
- 不假设所有效果都适用 `create/viewer/update/destroy` 完全统一的类型；按实际能力设计。

### Step E-03：资源与行为

- 明确谁拥有 Cesium 对象，谁负责销毁；将插件新增的 Primitive、Entity、PostProcessStage、监听器和动画回调妥善清理。
- 不破坏用户原有 viewer.scene 的状态；如必须暂时覆盖，保存并在适用时恢复原值。
- 初始化、更新、销毁、重复创建、部分初始化失败时的清理行为必须验证。
- 若依赖 Cesium 实验性 API，需记录并限制已测试版本，而非盲目宽泛声明兼容。

### Step E-04：真实包验证

- 包必须不依赖 `apps/playground`、`experiments`、内部路径别名、临时模拟资源。
- 构建 ESM 与类型声明，检查 `exports`、side effects、peer deps、实际产物及发布清单。
- 在仓库外或隔离目录中**安装真实打包产物**（tarball），完成消费端构建、浏览器运行和效果创建/销毁验证；只用 workspace 链接不能替代。
- 对照 Visual Approved 基线，确认无明显视觉退化；出现退化要修复或重新提交用户决定。

### Step E-05：提交发布候选

- 提交变更概述、使用示例、兼容范围、文档、测试报告、公开资产/许可检查、预期版本与风险。
- 等待用户正式发布批准。不得将 `git push`、创建 tag 和 `npm publish` 默认合并为自动操作。

## 6. 变更保护与回归

新增实验默认不得修改其他实验的相机、参数与已批准基准。必要的共享改动：

1. 列出受影响实验与公共模块。
2. 对原视觉基准检查高风险场景；确保测试条件与版本一致。
3. 构建、进入/退出、对象清理、浏览器错误进行回归检查。
4. 若旧实验不兼容，公开档案保留并按真实状态标注，不能通过删除档案掩盖。
5. 重大设计变更写入简短 ADR（背景、方案、替代、影响）。

Git 保留代码历史，Playground 不必实现 Git 操作；禁止未授权强制推送、历史清洗、删除他人文件。

## 7. 最小质量验证矩阵

| 工作类型          | 必须验证                                                       | 条件要求                   |
| ----------------- | -------------------------------------------------------------- | -------------------------- |
| 新建实验          | 元数据有效、页面可运行或明确不可运行、实际画面检查、技术说明   | 没有视觉工具必须声明未验证 |
| 修改视觉参数      | 参数变化可见、重置符合预期、原展示未退化                       | 适用参数存在时             |
| 修改 Runtime/构建 | Gallery、已有可运行实验的加载和退出、Cesium Workers 与静态资源 | 跨实验影响必测             |
| 修改正式包        | 构建、类型、资源清理、集成测试、视觉回归                       | 独立消费产物必测           |
| 发布候选          | 许可证、资产、依赖、包内容、SemVer、迁移、审批                 | 必须有人类发布批准         |

### 7.1 视觉验收记录最小字段

- experimentId、Git revision、目标参考描述或经授权的文件路径
- 画面比例/截图尺寸、默认相机、关键参数、（动态时）采样时间点
- 实际截图/动画证据路径与来源、运行环境（浏览器/OS/GPU 若可获取）
- 已满足的视觉特征、仍存在的差异、已知问题、用户最终结论

不要编造性能数值或“像素级相似度”。不同硬件/驱动可能生成不同输出，截图差异需要结合环境解释。

## 8. 安全和合法使用规范

- 不把第三方概念图当作自己生成的真实渲染结果。
- 不将无公开许可的第三方视觉参考、模型、视频、摄影资料随公开站点或 npm 包发布。
- 不把具有权限的 API 密钥提交 Git；前端暴露的服务令牌必须限制权限和配额，不能假定客户端 token 私密。
- 不添加用户上传任意 JS 立即在公开服务运行的功能；已登记实验通过仓库审核与构建发布。
- 不引入来源不明或有不兼容许可证的代码、Shader 或素材；必要时给出替代方案。
- 发现重大安全问题、可能产生费用或数据破坏的操作时停止并请求批准。

## 9. Agent 输出格式（每次任务交付）

建议以固定的简洁报告呈现，不要求每次产生额外 UI：

```text
任务：<实验 / 工程 / 维护>
变更：<做了什么>
运行入口：<URL 或命令及目录>
实际验证：<通过的命令、浏览器结果、截图/视频路径>
未验证：<原因与用户可执行的检查方式>
视觉匹配：<已达到的目标 / 差异>
实现解释：<原理、选择理由、限制>
风险：<兼容性、依赖、素材版权、性能>
所需用户决策：<如无则写无；视觉通过和 npm 发布必须单独确认>
```

如果该任务只是文档/架构更新，报告中应标明“未进行渲染测试（本次未改动视觉代码）”，而不是强制编造截图。

## 10. 专项执行模板

### 10.1 新视觉实验

```text
请基于提供的视觉参考在 cesiumlab 新增实验：
- 首先总结可观察的视觉目标与不可观察的假设；
- 选择能够实现视觉效果的 CesiumJS 技术路线；
- 真实启动 Web 页面、检查渲染并迭代；
- 保留实验档案、运行证据、原理与局限；
- 不提前将其封装进 packages/effects；
- 最后交付给我进行视觉验收，不得自行标记 Visual Approved。
```

### 10.2 已验收实验通用化

```text
此实验已获得我的视觉批准。请先评估是否值得通用化；
如果适合，再将其独立封装为 @cesiumlab/effects 的候选模块，
保留视觉基准，完成生命周期、类型、兼容性和外部安装测试。
不要直接发布 npm；提交候选包与验证结果供批准。
```

### 10.3 维护

```text
修复指定问题，尽可能限定变更范围；
不要无故更改已批准的视觉表现或公共 API；
执行相关回归检查，明确实际验证和未验证的项目；
若涉及破坏性变更，请先提出迁移和版本方案。
```

## 11. AGENTS.md 与细则关系

仓库根目录 `AGENTS.md` 应保持短且可执行，包含目标、权限、工作流与指向本文的链接。本文属于详细规范；架构、具体代码实现和测试事实以当前仓库为准。若存在规范冲突，先遵守安全与明确用户决定；不得擅自改变用户已确认的产品定位。任何新增强约束要同步更新文档并解释其对实验自由度的影响。

## 12. 发布前最终批准项

发布之前检查：

- [ ] 用户已明确批准发布及拟发布版本
- [ ] npm scope / 仓库归属已确认
- [ ] 许可证、第三方资产与源码发布权限已确认
- [ ] 包产物及 public files 清单已审查
- [ ] 独立项目安装真实 tarball 后可成功运行
- [ ] 兼容版本、破坏性变化与迁移文档已确认
- [ ] 视觉回归与生命周期测试有证据
- [ ] npm 认证方式 / 受保护发布工作流准备就绪

未满足时，只能交付候选包，不得声称已经发布。
